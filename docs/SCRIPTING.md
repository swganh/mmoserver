# Scripting: current state and roadmap

Goal: an engine/content split. The C++ servers provide the mechanics
(networking, world, combat, persistence); game content (the tutorial,
quests, spawns, NPC behaviour) lives in Lua scripts that can be changed
without rebuilding. Everything stays GPL, as the code it builds on is; the
split is about who can change what, and how easily, not about closing the
core.

This follows the model SWGEmu's Core3 uses. Written after taking a character
through the whole tutorial on Linux (see `docs/KNOWN_ISSUES.md` for what was
fixed on the way); file and line references are to the tree at the time.

## Content sources

Content is recreated from what the client ships and from public
descriptions of the original game: the client's string files
(`newbie_tutorial/system_messages`, `newbie_tutorial/newbie_convo`, ...)
and sounds (`sound/tut_*.snd`), which the scripts already reference, plus
recordings and wiki write-ups of how things played. The leaked SOE server
source is not a source: it was never licensed, and porting or translating
it would put the project and everyone who hosts it at legal risk.

## What exists today

### Engine

- **Lua 5.1**, one `lua_State` per zone, each script running as a
  coroutine (`src/ScriptEngine/Script.cpp`). `LuaScriptEngine.WaitMSec`,
  `WaitTime` and `WaitFrame` yield; `ScriptEngine::process`, called every
  zone tick, resumes scripts whose wait is over. Timing is real elapsed
  milliseconds.
- **Bindings** are generated by tolua++ from the `.pkg` files in
  `src/ScriptEngine/glue_files/` into `LuaInterface.cpp`, which is checked
  in. Regenerating uses `make_glue.bat` and a bundled `tolua++.exe`
  (Windows only); there is no Linux path yet.

  | Package | Functions | What for |
  |---|---|---|
  | `LuaTutorial.pkg` | 49 | tutorial state, UI elements, prompts, player position |
  | `LuaScriptSupport.pkg` | 32 | create/spawn/move NPCs, items, fly text, kill/isDead |
  | `LuaWorldManager.pkg` | 6 | world queries |
  | `LuaObject.pkg`, `LuaCommonMessages.pkg` | 4 | misc |

- **Events** are thin: world scripts get `onPlayerEntered` and
  `onPlayerLeft`; command scripts can hook object controller commands
  (`ObjectControllerCommandMap`); the tutorial registers its own listener.
  Everything else is polled (see below).

## Layout

Agreed November 2026; `data/script/README.md` has the folder table and the
conventions. In short:

```
data/script/
  lib/              shared modules (require 'script/lib/...')
  world/common/     every planet: weather, login messages
  world/<planet>/   one planet's world scripts
  tutorial/         the new-player tutorial
  commands/         command hooks
  ai/               behaviours: patrol, formation, wander, lair defence
  spawns/<planet>/  static NPCs, patrols, spawn regions
  conversations/    dialogue trees for quest givers and named NPCs
  quests/<planet>/  quest chains
  themeparks/       Jabba, Imperial, Rebel, Nym
  missions/         mission terminal templates
  dev/              tests and experiments, not for live servers
```

The split: **C++ is the engine** (network, object model, spatial grid,
database, movement, combat maths, crafting mechanics, persistence), **Lua is
behaviour** (what NPCs, quests, the tutorial and events do), and **the
database is data** (loot tables, trainers, item stats, spawn tables): content
that only needs a table does not need a script.

What moves out of C++, roughly in this order:

| Content | In C++ today | Moves to |
|---|---|---|
| Tutorial | `Tutorial.cpp`, 38 `isTutorial()` checks in 20 files, hard-coded NPC and terminal ids | `tutorial/` on event hooks |
| Quest givers | `QuestGiver.cpp` checks NPC ids per conversation outcome | `conversations/`, `quests/` |
| NPC spawns and patrols | `NpcManager`, spawn regions, the `dev/` tests | `spawns/`, `ai/` |
| Creature behaviour, lairs | `AttackableCreature`, `LairObject` (largely stripped) | `ai/`, with C++ keeping the primitives (move, attack, aggro events) |
| Theme parks | not implemented | `themeparks/`, on the quest API |
| Mission targets | `MissionManager` | `missions/` templates; the terminal stays C++ |
| Badges by region | `BadgeRegion` | `world/` or an event hook |
| Trainers, loot | C++ and tables | stay data in the database |

The `dev/` scripts' useful parts (formation movement, NPC spawning) become
`ai/` and `lib/` modules; the tests themselves stay in `dev/` and are to be
disabled on Tatooine once something real replaces what they show.

Moving a script that the database names needs a migration
(`mmoserverdb/migrations`, applied by `setup.sh install`, `migrate` and
`update`); CI checks that every script path in the database exists.

## What is wrong with it

### Tutorial content is split between Lua and C++

| In the Lua script | Hard-coded in C++ |
|---|---|
| step sequence, prompts, sounds, waits | travel terminal ids and the quartermaster's "release documents" line (`TravelTerminal.cpp:67-97`) |
| NPC ids, spawn positions, debris, bandit | conversation outcomes per NPC id: the covard officer moves the script to step 17, quartermaster, mission room officer (`QuestGiver.cpp:103-370`) |
| position triggers | starting cell (`Tutorial.cpp:100`), starting-location lookup and warp (`Tutorial.cpp:166`) |
| | mission terminal id (`MissionTerminal.cpp:52`) |
| | 38 `isTutorial()` checks in 19 files (combat, food, trainers, cloning and insurance terminals, spawning, fly text) |

A change to the tutorial's flow can need edits in the script, in up to a
dozen C++ files, and in the database.

### Scripts poll instead of reacting

The tutorial loops on `WaitMSec(500)` and checks `npcIsDead`,
`isNpcConversationStarted`, `getPlayerPosX` and so on. Consequences seen in
testing: prompts trail behind a quick player, and a check that only runs
after a position trigger (the debris death) looks like the script is not
tracking what the player did.

### Ids and data in the script

Object ids, cell ids and positions are literals in the script and in C++.
They match one database; another export of the data or a rebuilt tutorial
building breaks them silently.

### The bindings are hard to change

Adding a function means editing a `.pkg` file and regenerating
`LuaInterface.cpp` with a Windows-only tool, and tolua++ itself is
unmaintained (the build fetches its source from the Ubuntu archive).

## Roadmap

Each step leaves the tutorial working; test it end to end with a client
after each.

### 1. Inventory

- Walk the tutorial with the original's public descriptions next to the
  script and list, per step: what the player should see and do, what the
  script does, what C++ does. Mark gaps (the missing destination prompt at
  step 26, the debris explosion, the "[]:" bark).
- List every `isTutorial()` and `isInstance()` branch and every hard-coded
  content id in C++ (the tables above are the start).
- Compare with what [swganh](https://github.com/anhstudios/swganh) put in
  scripts (commands, radials, attributes, buffs, spawns, weather, character
  creation); see "Prior work" in `docs/ROADMAP.md` for how to use it.
- The `dev/` test scripts: their useful parts become `ai/` and `lib/`
  modules (see Layout); then disable them in `config_zone_scripts` with a
  migration.

### 2. Event hooks

Add events that scripts can wait on instead of polling, raised from the C++
places that already know: creature died, conversation started/ended (with
the option chosen), player entered cell or region, item looted, object used
(radial menu), skill trained. In Lua this is a wait that yields until the
event or a timeout:

```lua
local event = LuaScriptEngine.WaitEvent("creature_died", npcDebrisId, 60000)
```

The coroutine model makes this a small change to `Script`: a new wait state
resumed by the event instead of the clock.

### 3. A small, documented script API

Group what content needs into a few modules (world: spawn, despawn, move,
warp; npc: converse, bark, animate, set attackable; player: message, sound,
give item, UI elements, grant skill; data: look up objects by name rather
than id) and document each function. Content-specific behaviour moves out
of C++ into script callbacks, e.g. a quest giver's conversation outcome
calls the script instead of `QuestGiver.cpp` checking NPC ids.

### 4. Move the tutorial onto it

Rewrite `tutorial/part1.lua` against the new API and events, step by
step, and delete the tutorial branches from C++ as each moves. Ids come
from the database or named lookups. Then the same for quests and spawns.

### 5. Bindings

Keep Lua 5.1 (a project decision). Make the bindings buildable on Linux and Windows: either build
tolua++ as part of the build and regenerate `LuaInterface.cpp` from the
`.pkg` files, or replace tolua++ with a maintained header-only binding
(sol2 supports Lua 5.1) when the API in step 3 is written, binding only
that API.

## Fits with the wider plan

- **Windows build first.** Bindings (step 5) and the script engine have to
  build on both before larger changes; the Windows build is the next phase
  of the revival plan.
- **Dependency upgrades and refactoring** (later phase): the C++ that the
  script API wraps is where most of the bugs found in testing were (NPC
  visibility, death, posture, spawning), so stabilising those mechanics
  comes before moving content onto them.
- **Tests.** The script engine and an event-driven API can be unit tested
  (a script waiting on an event, resumed by it) without a client; the
  ZoneServer has no unit test target yet (its `main` is in
  `ZoneServer.cpp`, which the test layout in `MMOServerExecutable.cmake`
  expects in `main.cpp`).
